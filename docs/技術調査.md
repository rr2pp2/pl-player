## 0. 結論の一覧

| 原文の調査項目 | 第一候補でできるか | 一言 |
|---|---|---|
| 音声再生ライブラリ（7形式） | **危うい** | 6形式は Rust 純正のデコーダで足りる。**Opus だけが未対応**で、C の libopus を足す必要がある。HE-AAC の m4a も未対応 |
| Windows Audio Device API | できる | cpal（WASAPI）で一覧・指定デバイスへの出力・切断の検知ができる。追加・削除の通知は Windows API を直接使う |

**第一候補の5つ（Tauri・React・TypeScript・Rust・SQLite）は、そのままで成り立つ。**

## 2. 音声再生ライブラリ

### 2-1. 形式ごとの判定（Symphonia 0.6.1 の公式表による）

| 形式 | 入れ物（デマルチプレクサ） | 中身（デコーダ） | 判定 |
|---|---|---|---|
| MP3 | ― | MP3：Excellent | できる |
| WAV | WAV：Excellent | PCM | できる |
| FLAC | FLAC：Excellent | FLAC | できる |
| M4A | MP4/M4A：Great | AAC-LC：Great／ALAC：Great／**HE-AAC・HE-AACv2：未実装** | **危うい**（AAC-LC と ALAC は通る。HE-AAC の m4a は再生できない） |
| AAC（ADTS） | ADTS（Symphonia に含まれる。※公式表の抜粋では行を確認できず、**未確認**） | AAC-LC | **未確認**（実装の最初に実ファイルで確かめる） |
| OGG | OGG：Great | Vorbis：Excellent | できる |
| OPUS | OGG：Great | **Opus：未実装（"-"）** | **できない（Symphonia 単体では）** |

根拠：https://github.com/pdeljanov/Symphonia （README の対応表）

**v3.1.2 の追記：**HE-AAC は、Symphonia がデコーダを作れない AAC のときだけ Windows の Media Foundation（Source Reader と AAC デコーダ。HE-AAC v1・v2 を読むと公式にある）で読む形にした。
根拠：https://learn.microsoft.com/en-us/windows/win32/medfound/aac-decoder ／ https://learn.microsoft.com/en-us/windows/win32/medfound/source-reader

### 2-2. Opus を埋める手段

| 手段 | 中身 | 引っかかる点 |
|---|---|---|
| **symphonia-adapter-libopus 0.3.0** | Symphonia 0.6 に libopus のデコーダを足す部品。既定で libopus を**ソースから組む** | 組むのに **CMake と C コンパイラが要る**（opusic-sys の README）。手元では CMake が PATH に無い。libopus は BSD-3 |
| Windows Media Foundation | OS 標準のデコーダ | Microsoft の公式表に **Opus・Ogg・Vorbis・FLAC の記載が無い**。M4A・AAC・MP3・WAV は載っている。全形式をこれに寄せることはできない |

根拠：
- https://crates.io/api/v1/crates/symphonia-adapter-libopus （依存は `symphonia-core ^0.6`・`opusic-sys ^0.7.3`。`bundled` 機能が既定）
- https://github.com/DoumanAsh/opusic-sys （`bundled` には cmake が要る）
- https://learn.microsoft.com/en-us/windows/win32/medfound/supported-media-formats-in-media-foundation

### 2-3. rodio を使わない理由（音声エンジンの組み方に関わる）

**rodio 0.22.2 は Symphonia を 0.5 系（`^0.5.5`）、cpal を 0.17 系で使っている。**
**Opus を足す部品は Symphonia 0.6 系が前提**なので、rodio の中のデコーダには差し込めない。
さらに rodio の README は「音声エンジンの中核を書き直している最中」と書いている。

**だから音声エンジンは「Symphonia 0.6（デコード）＋ cpal 0.18（出力）＋ rubato（サンプルレート変換）」で自前に組む案にした。**
原文の「後から全面的に作り直すことがないように」に対して、いちばん手戻りが少ない形。

根拠：
- https://crates.io/api/v1/crates/rodio/0.22.2/dependencies
- https://github.com/RustAudio/rodio
- https://crates.io/api/v1/crates/rubato （5.0.1、MIT OR Apache-2.0）

## 3. Windows Audio Device API

| 要求 | 判定 | どう実現するか |
|---|---|---|
| 出力デバイスの一覧 | できる | cpal（WASAPI が既定）。0.18.2 で表示名が FriendlyName 優先になった。デバイスを安定した ID で引ける |
| 再生中の切り替え（曲と位置を保つ） | できる | 出力（cpal のストリーム）だけを作り直し、デコーダの状態は保つ。位置は「実際に鳴らしたフレーム数」で持つ（設計は `アーキテクチャ案.md` 4章） |
| 切断の検知とフォールバック | できる | cpal のエラーコールバックに `DeviceNotAvailable`・`StreamInvalidated` が来る。0.18.0 から、既定デバイスで開いたストリームは既定の変更に自動で追従する（`DeviceChanged`） |
| 一覧の自動更新（抜き差し） | できる（cpal の外） | Windows の `IMMNotificationClient`（OnDeviceAdded／Removed／StateChanged／DefaultDeviceChanged）。**コールバックの中で待たない・登録解除しない**、と公式に制約がある |

根拠：
- https://github.com/RustAudio/cpal
- https://raw.githubusercontent.com/RustAudio/cpal/master/CHANGELOG.md （0.18.0 の自動追従、0.18.2 の FriendlyName）
- https://raw.githubusercontent.com/RustAudio/cpal/master/src/error.rs （エラー種別。**master の内容で、0.18.2 と完全に同じかは未確認**）
- https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient

## 4. Windows Global Hotkey

| 要求 | 判定 | 根拠 |
|---|---|---|
| バックグラウンドで効く | できる | Tauri 公式 `tauri-plugin-global-shortcut` 2.4.0（中身は `global-hotkey` 0.8.0） |
| キーを個別に設定 | できる | 登録・解除・登録済みかの確認が API にある。権限は既定で全部オフなので、`allow-register`・`allow-unregister`・`allow-is-registered` を明示して許可する |

**注意（公式記載）：** F12 はデバッガ用に予約されていて登録しない。Win キーを含む組み合わせは OS 用に予約されている。

根拠：
- https://v2.tauri.app/plugin/global-shortcut/
- https://raw.githubusercontent.com/tauri-apps/global-hotkey/dev/src/error.rs
- https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey

## 5. Windows Media Session（SMTC）とメディアキー

| 要求 | 判定 | 根拠と方針 |
|---|---|---|
| メディアキー（再生/一時停止・次・前） | できる | SMTC に登録すれば、キーボードのメディアキーと OS の音量フライアウトの操作がアプリに届く |
| 曲名・アーティスト・アートの表示 | できる | `SystemMediaTransportControlsDisplayUpdater` |
| 再生位置の表示とシーク | できる | `SystemMediaTransportControlsTimelineProperties`・`PlaybackPositionChangeRequested` |
| Win32（Tauri）から使えるか | できる | `ISystemMediaTransportControlsInterop::GetForWindow(HWND)` で取る |

**既製の部品 souvlaki 0.8.3 は、上の API をそのまま使っている**（ソースで確認）。
ただし**最終更新が 2025-06-24 で、使う `windows` クレートが 0.44**（現行は 0.62.2）。Tauri 側が使う版と二重に入る。
**推す案：同じ API を `windows` 0.62 で自前に書く（150〜250行ほどの見込み）。**souvlaki はその手本として読む。どちらにするかは `依存の候補.md` に並べた。

**自動連携は使えない：** 公式文書のとおり、SMTC への自動登録は `MediaPlayer` クラスで鳴らしたときだけ。PL Player は自前のエンジンで鳴らすので、**手動で登録する**。

根拠：
- https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/integrate-with-systemmediatransportcontrols
- https://learn.microsoft.com/en-us/windows/win32/api/systemmediatransportcontrolsinterop/nn-systemmediatransportcontrolsinterop-isystemmediatransportcontrolsinterop
- https://github.com/Sinono3/souvlaki ／ https://raw.githubusercontent.com/Sinono3/souvlaki/master/src/platform/windows/mod.rs
- https://crates.io/api/v1/crates/souvlaki/0.8.3/dependencies

## 6. Taskbar Media Controls

**原文の「タスクバーのメディア操作」は2つに分かれる。**

| 何か | 判定 | 方針 |
|---|---|---|
| A. タスクバーのサムネイルに出るボタン（前・再生/一時停止・次） | できる | `ITaskbarList3::ThumbBarAddButtons`。最大7個。**後から足し引きできない**ので最初に全部定義し、表示の切り替えは `ThumbBarUpdateButtons`。押されると `WM_COMMAND`（`THBN_CLICKED`）が来るので、ウィンドウのメッセージを横取り（サブクラス化）して受ける |
| B. Windows 11 のクイック設定などに出るメディア操作 | できる | 5章の SMTC で出る |

**Tauri にはサムネイルボタンの機能が無い**ので、`windows` クレートで直接書く。

根拠：https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itaskbarlist3-thumbbaraddbuttons

## 7. タグ読み書きライブラリ

**lofty 0.25.4（2026-09-20 更新、MIT／Apache-2.0）。**

| 形式 | 読み書きするタグ |
|---|---|
| MP3 | ID3v2（ID3v1・APE も読める） |
| FLAC | Vorbis Comment（FLAC 内の ID3v2 は**読むだけ**） |
| M4A | iTunes 形式（ilst） |
| OGG／OPUS | Vorbis Comment |
| WAV | ID3v2・RIFF INFO |
| AAC（ADTS） | ID3v2・ID3v1 |

原文の10項目（Title・Artist・Album・Genre・Year・Track・Disc・Composer・Comment・Artwork）は、
共通の取り出し口と `ItemKey`（Composer など）、`Picture`／`push_picture`／`remove_picture` で扱える。

**安全な書き込み（原文：一時ファイル→検証→置換）：**
1. 元ファイルと**同じフォルダ**に一時ファイルとして複製する（置換は同じドライブの中でしかできないため）
2. 一時ファイルにだけ lofty で書く
3. 一時ファイルを lofty で読み直して値を照合し、Symphonia で頭の数フレームを実際に復号できるか確かめる
4. Windows の `ReplaceFileW` で差し替える。作成日時・アクセス権などは元のものが引き継がれる
5. 途中で失敗したら一時ファイルを消して元は触らない。失敗の種類ごとに日本語で知らせる

根拠：
- https://github.com/Serial-ATA/lofty-rs ／ https://docs.rs/lofty/0.25.4/lofty/
- https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew

## 9. 外へ出る通信（作者の作業ルールの観点）

**アプリ本体は通信しない設計にできる。**曲もタグもアートも全部ローカルで読む。
**ただし、作る過程で外へ出る通信が3つある。**

| いつ | 何が | 避けられるか |
|---|---|---|
| 依存を落とすとき | crates.io と npm からの取得 | 避けられない。**作者の承認が要る** |
| 配布用ビルド（NSIS）のとき | Tauri のビルド道具が **NSIS 3.11 と nsis_tauri_utils.dll を GitHub から自動で落とす**（`%LOCALAPPDATA%\tauri\NSIS` に置く）。https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-bundler/src/bundle/windows/nsis/mod.rs | 一度落とせば以後は手元のものを使う。**MSI（WiX）の取得も同じ形と推定するが、未確認** |
| 配布物を入れるとき | 既定の `downloadBootstrapper` は、入れる側の PC で WebView2 を取りに行く | 設定で `offlineInstaller`（約127MB増）か `skip` にすれば通信しない。この PC には WebView2 154 が入っている。https://v2.tauri.app/distribute/windows-installer/ |

**Tauri CLI 自体が利用状況を送るかは、確かめられなかった（未確認）。**npm の `@tauri-apps/cli` 2.12.1 には install 時に走るスクリプトが無いことだけ確認した。落とした後に 作者の作業ルールの検査で確かめる。
